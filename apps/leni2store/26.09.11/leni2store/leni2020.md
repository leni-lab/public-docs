# LENI2020 interface

This contract describes the file handoff from LENI2020 to leni2store.

Regular LENI2020 distribution exports have no future send time: LENI2020 holds
scheduled messages until `transmit_at` is due before exporting them. leni2store
therefore does not schedule delivery. See
[LENI time semantics](https://github.com/leni-lab/leniextract/blob/main/docs/time-semantics.md)
for the publication lifecycle and the preview exception.

## Producer responsibilities

- write each export in one open-write-close operation
- keep the file open for the entire write so the Windows exclusive-access
  check cannot succeed while content is still being written
- do not modify, replace, or reopen the completed file for writing
- generate filenames independently of files remaining in the export directory
- run one name-generating producer process per export directory
- leave processing directories to the importer

Export names must follow the
[newsstore contract](https://github.com/leni-lab/newsstore/blob/main/docs/store-contract.md),
with source `leni`, for example `1789203039_001.leni.json`. leni2store preserves
names and does not validate or convert the naming scheme.

In the LENI export code inspected on 2026-09-25, `export_published` assigns
`data.released_at` and `data.published_at` from the processing-time value `$^T`
before calling `export_dist`. The timestamp in the filename uses the same
value, so it matches both fields on this publication path. `export_dist`
itself does not read or validate those fields, so a different direct caller
would not have that guarantee.

The newsstore contract calls this filename timestamp `released_at`: the
source release for distribution to subscribers. leni2store preserves it
without reading the JSON or assigning an arrival time. The original LENI
field names remain unchanged. Release for distribution does not itself
permit public publication before an applicable embargo expires.

Within one producer run, a timestamp greater than all previously assigned
timestamps resets the suffix to `001`. Equal or backward time values increment
the suffix. The filename always uses the current processing-time value, even
when it moves backward. Filename timestamps are therefore not guaranteed to
increase monotonically.

After a restart, the first export second must be greater than every timestamp
used before shutdown to avoid reusing names. With a normally advancing clock,
a full second after the last export is sufficient. A backward clock adjustment
can require a longer wait. The in-memory suffix alone does not protect across
restarts.

## Importer responsibilities

- watch one directory over Windows filesystem access, including SMB
- select matching files directly in the source directory
- wait for the configured stability window and skip files with active access
- move ready files into `work` before copying
- copy bytes without parsing JSON, preserving the name and modification time
- publish each completed destination file atomically under its final name
- treat an existing regular destination file as successfully processed
- archive successful sources in the configured `done` directory
- retain failed files in the standard retry, failure, or review directories

## Delivery and recovery

Run one importer instance for this source. No ordering between different files
is guaranteed.

An interrupted import can be attempted again. Destination existence is the
completion check. Destination files are retained for at least 24 hours in the
agreed deployment. If a destination has later disappeared while a recoverable
source still exists, recreating it is acceptable.

The final filename guarantees a complete published copy during normal operation.
It is not a separate guarantee against storage hardware failure or power loss.
